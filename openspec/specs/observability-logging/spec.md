# observability-logging Specification

## Purpose
Provides HTTP request and response observability, request tracing with correlation IDs, and runtime logging control for the Alea Pokémon API.

## Requirements

### Requirement: Request and response logging
The system SHALL record an access log entry for every incoming HTTP request containing the HTTP method, request URI, HTTP response status code, and execution duration in milliseconds.

#### Scenario: Request completes successfully
- **WHEN** an HTTP request is processed by any `/api/v1/pokemon/*` endpoint
- **THEN** the system logs the HTTP method, request URI, 200 status code, and duration in ms

#### Scenario: Request fails with error status
- **WHEN** an HTTP request results in a 4xx or 5xx error status code
- **THEN** the system logs the error status code, request URI, and processing duration

### Requirement: Correlation ID propagation
The system SHALL generate a unique `X-Correlation-Id` for requests without one, preserve incoming correlation IDs, and attach the ID to both SLF4J MDC and HTTP response headers.

#### Scenario: Request without existing correlation ID
- **WHEN** a client issues a request without an `X-Correlation-Id` header
- **THEN** the system generates a UUID, binds it to MDC for all log statements, and returns `X-Correlation-Id` in the response headers

#### Scenario: Request with existing correlation ID
- **WHEN** a client supplies an `X-Correlation-Id` header
- **THEN** the system retains that identifier in MDC and echoes it in the `X-Correlation-Id` response header

### Requirement: Configurable logging levels
The system SHALL support configuring log levels in `application.yaml` with formatted output including timestamp, level, logger name, correlation ID, and message.

#### Scenario: Standard logging output
- **WHEN** a log statement is generated by the application
- **THEN** the log line includes timestamp, thread name, log level, logger name, correlation ID from MDC, and log message
